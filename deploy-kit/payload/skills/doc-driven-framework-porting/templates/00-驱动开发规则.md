## 一、这套框架解决什么问题

框架不是凭空设计的，它来自真实项目踩过的坑。下面四类问题反复发生过，每类各配一个机制。

| 已实际发生过的问题 | 对应机制 |
|---|---|
| **口头结论丢失**：跨会话讨论的关键决定没落档，后续会话无人知晓 | 落档纪律 |
| **文档滞后于现实**：文档说 A，代码已经是 B，没人知道以谁为准 | 证据裁决 |
| **流程尾步遗漏**：功能"看起来做完了"，验收 / 文档 / 提交缺一环 | 对账验收 |
| **需求-实现脱节**：AI 理解的需求，和人类真正想要的效果不是一回事 | 闭环工作流 |

一句话定位：**用五份固定文档 + 一个总验收命令，把「人类提需求、AI 做实现」的协作过程变成可回流、可审计、可交接的闭环。**

> **大白话版**：这套东西相当于给项目配了一本**双方共用的工作台账**——你说要什么（记在 01），我写清打算怎么做（02、03），做的过程随手记账（04），最后有一条命令像"对账单"一样自己核一遍。好处是：隔了半个月开一个新会话、或者换个人来接手，翻台账就能接上，不用从头再讲一遍故事。

## 二、核心机制（四条，框架的心脏）

1. **闭环工作流**——需求到验收的可回流循环，不以首次开发完成为终点。
2. **落档纪律**——关键结论当轮进文档；流程尾步未完成视为任务未完成。
3. **证据裁决**——多路证据冲突时的固定优先级。
4. **对账验收**——恰好一个人类可独立执行的验收命令，文档里说的事实必须能被脚本对账。

其余内容（五文档分工、编号引用、文档生命周期、领域扩展）都是围绕这四个机制的组织形式。

## 三、五文档体系 + 根入口 + 三层架构

**根入口存在的理由**：新会话（人或 AI）不该全量读文档，而应从 tokens 最少的入口按需下钻。它同时是「结构性变更必须同步」的载体（见第六节第 4 条）。

| 文档 | 主要写什么 | 谁说了算 |
|---|---|---|
| `00-驱动开发规则.md` | 工作流、文档分工、协作规则、安全与交付底线、领域扩展 | 人类批准边界条款；AI 维护 |
| `01-人类需求描述.md` | 项目目标、需求条目、约束、验收标准、使用反馈 | **人类主权**；AI 受托整理 |
| `02-需求技术拆解.md` | 需求的技术理解、技术事项、疑问与假设 | AI 全权 |
| `03-技术实现方案.md` | 实现思路、关键设计、测试方案 | AI 全权 |
| `04-实现过程记录.md` | 里程碑、关键证据、偏差、限制、踩过的坑 | AI 全权 |
| `START_HERE.md` | 根入口：四层阅读路径 | AI 全权，结构变更同轮同步 |

**三层架构**（行为层是全项目共享的用户级技能，不随项目走）：

| 层 | 载体 | 职责 |
|---|---|---|
| 事实层 | `00–04` 五文档 + `START_HERE.md` | 项目状态与证据，唯一事实源 |
| 行为层 | 用户级技能 `doc-driven-dev`（`~/.workbuddy/skills/`） | 闭环六步、收尾四步、即时对齐审计、权限矩阵、红线自动加载 |
| 触发层 | ~~定时任务~~（默认不建，人类可裁决） | 无人值守审计由行为层的「即时对齐审计」替代 |

**文档权限矩阵（硬规则）**：

| 文档 | 人类 | AI |
|---|---|---|
| `00` | 读；批准边界类条款变更 | 写。安全底线 / 交付纪律 / 文档权限等**边界条款改动须人类批准** |

## 四、编号引用体系

- 固定前缀：`REQ-xxx`（01 需求）/ `TECH-xxx`（02 技术事项）/ `D-xxx`（03 关键设计）/ `M-xxx`（04 里程碑）/ `ASM-xxx`（04 假设登记簿）/ `Q-xxx`（待人类裁决）/ `C-xxx`（约束）/ `A-xxx`（验收标准）/ `SEC-xxx`（安全条款）。
- 新需求、设计、实现、验收分别并入 `01/02/03/04`，靠编号跨文档连接，**不按需求新建说明文件**。
- 正式文档固定为 `00–04` 五份 + 根入口。只有内容确实无法归入、需要长期独立维护、有明确读者、且不与现有内容重复时，才经人类批准后新增。
- `01–03` 只留当前有效内容，失效内容更新或删除；`04` 保留关键事实与证据。
- **编号即索引**：任何文档里的声明都能靠编号追到来源（REQ 从哪来、被哪个 TECH 实现、哪个 D 定了口径、哪个 M 验收）。

## 五、闭环工作流（六步循环）

1. **人类**在 `01` 说明目标、需求、约束和验收标准。需求条目采用 **EARS 句式**：「**当〈触发条件〉时，系统应〈可验证的响应〉**」——禁止"系统应该快一点"这类无法验证的模糊表述；人类说的"我怎么判断效果好"，由 AI 转写成可验证的验收条款（A-xxx）。
2. **AI** 读需求，在 `02` 转化为可实现的技术事项；有歧义先提问（登记 `Q-xxx`），或写明保守假设（登记 `ASM-xxx`）后继续推进。
3. **AI** 在 `03` 设计具体实现方式和测试方法：关键设计要定口径、公式、交互规则，并给可手工对账的验收样例。
4. **AI** 按方案开发，在 `04` 持续记录完成情况、重要调整和测试结果（按里程碑 `M-xxx` 组织）。
5. **人类**依据 `01` 的验收标准检查最终结果（跑总验收命令）。需求变化时，先更新 `01`，再同步后续文档与实现。
6. **使用反馈**先进入 `01` 的反馈区，确认后形成新 `REQ` 或修订既有 `REQ`，再进入下一轮。

流程可以往返循环，**不以首次开发完成为终点**。简单项目写得很短，复杂项目按需增加细节。

## 六、落档纪律（四条）

1. **关键结论当轮落档**——对话中产生的关键结论，尤其是人类的意图澄清、边界声明、授权与拒绝，必须在当轮写入 `01` 或 `04`。**没有落档的结论，对后续会话不存在。**
2. **任务完成 = 流程尾步全完成**——实现、测试、验收、文档记录、版本提交全部完成才算完成。**验收通过但工作区有未提交变更，视为任务未完成。**
3. **歧义处理分级**——AI 主动识别歧义、隐含条件与风险边界。能靠保守假设推进的，登记假设后直接做，事后验证；会根本改变含义的问题**必须中途停下来问人类**。
4. **结构性变更须同步根入口**——凡新增 / 删除目录、子系统、核心文件，或某模块状态重大变化（暂停 / 完成），必须在同一变更中更新 `START_HERE.md` 对应条目，保持入口与实际结构一致。

## 七、证据裁决规则

项目的真实状态由多路证据共同证明：文档、目录结构、版本历史、运行配置。冲突时按固定优先级裁决：

```text
运行配置  >  目录结构  >  版本历史  >  文档
```

文档排在最后，因为它最容易滞后。**任何与文档声明冲突的现实证据，都应触发文档修正，而不是被忽略。**（文档错了改文档，不是当没看见。）

## 八、对账验收（总验收命令）

每个项目必须提供**恰好一个**总验收命令（本项目为 `python verify.py`；Windows 工作站建议 `E:\anaconda\python.exe verify.py`），满足六项要求：

1. **人类可独立执行**——不依赖 AI 转述结果，命令输出就是结论。
2. **失败必须显式**——任一关键项失败返回非零退出码，不得把"看起来在运行"当成成功。
3. **硬事实可验证**——文档中的可量化声明（数量、状态、路径、配置）必须能被该命令对账。文档说的事实和脚本查出的现实不一致，就是验收失败。
4. **覆盖安全边界**——第十一节的安全条款必须纳入检查范围。
5. **自检运行环境**——先校验解释器版本、声明依赖可导入且版本达标；缺失时显式报告并给修复提示。环境是后续开发的地基，应前置验收，新增依赖时增量复验。
6. **结论绑定输入版本**——输出记录 git commit 哈希（有数据后加数据 schema 版本），结论只对该版本有效。

## 九、文档生命周期（防膨胀）

- **假设登记簿**：`04` 维护「未验证假设」小节，记录所有推进用的保守假设；每轮验收复查，证实或推翻后更新状态。
- **触发式归档（硬阈值：到点必须压，不是「应该」）**：

| 触发条件 | 必须执行的压缩动作 |
|---|---|
| 里程碑 > 20 条 | 已完成满 3 个月的压成一行索引（`M-xxx` + 一句话结论 + commit 哈希），细节交版本历史 |
| `04` 验收结论表 > 30 行 | 只留最近 10 行，其余按月压成归档索引 |
| `REQ` > 40 条 | 完成且被后续需求取代的条目退役为索引行（编号 + 一句话结论 + 取代者编号） |
| `04` 全文 > 400 行 | 立即执行上三项，直到回落到阈值内 |
| `START_HERE` 里程碑索引 > 20 条 | 同里程碑规则压缩为一行一条 |

> 阈值可按项目规模调整，但**不得取消**。`verify.py` 对 `04` 行数与里程碑条数做自动对账，超限即验收失败。
> 理由：**凡是没被脚本检查的规则，长期看都会退化**——这不是不信任谁，是注意力天然有限。
- **单功能规格 ≤ 800 行红线**（业界实测阈值）：任一功能的完整规格（该功能相关的 `REQ` + `TECH` + `D` 合计）超过 800 行，就必须拆成多个功能——文档太肥会让 AI 产出质量骤降。
- **问题 / 坑落点纪律**：开发或使用中发现的坑、被证伪的假设、可复用的经验，**当场落档**，不拖到下一轮。三类各归其位：
  ① 假设被证伪 / 过程偏差 → `04` 假设登记簿 + 时间线；
  ② 可复用的经验 → 技能或知识库；
  ③ 工程 / 环境约定 → 工作区记忆文件。
  同时把一句话结论登记进 `04` 顶部「**坑位速查表**」（日期 + 现象 + 根因 + 解法 + 落点），作为下次排错的快捷入口。

## 十、人类与 AI 的权责

- **人类**：确认需求、授权需求文档修改、验收结果、对高风险事项给单独明确授权。
- **AI**：辅助澄清需求、维护 `02–04`、执行实现与测试、主动暴露问题与偏差。
- AI **不得擅自改变人类需求**；可以为 `01` 提整理建议，但修改前须经人类确认与授权（人类已持续授权的事项除外）。

### 收尾四步（每轮沟通 / 推进完成后立即执行，缺一项即视为任务未完成）

## 十三、并行开发约定（多会话 / 多分支）

> 第三节的权限矩阵假设的是「**一个人 + 一个 AI**」。当同时开多个会话、多条分支推进时，
> `02` / `03` / `04` 会出现两个 AI 同时写入，**必须事先约定分工**——
> 否则冲突与编号撞车会在合并那一刻集中爆发，而那正是最不该出问题的时候。

### 13.1 文件主权（并行期间）

| 文档 | 并行期间谁写 |
|---|---|
| `00` | **冻结**（并行期间不改规则） |
| `01` | 人类（合并点唯一；任何分支都不得改动实质内容） |
| `02` / `03` | 各分支只写**自己新增的编号段**，不删除、不重排他人条目 |
| `04` | 各分支只**追加**自己里程碑的条目，不重排他人条目 |
| `START_HERE` | **冻结**，合并后由主线会话统一更新（避免每个分支各改一次入口） |

### 13.2 编号分段预分配（防撞号）

开工前由人类或主线会话分配号段，各分支**只用自己那一段**：

```text
主线      M-000 ~ M-099      REQ-001 ~ REQ-099
分支 A    M-100 ~ M-199      REQ-100 ~ REQ-199
分支 B    M-200 ~ M-299      REQ-200 ~ REQ-299
```

同样规则适用于 `TECH-` / `D-` / `ASM-` / `TD-` / `A-` / `C-` 等全部编号。
**预分配写在 `04` 顶部或 `START_HERE` 当前快照里**，让每个会话都看得见自己的号段。

### 13.3 合并纪律

1. 各分支合并前**自跑** `verify.py`，必须全绿；
2. 合并后由**主线会话统一再跑一次**——跨分支的编号引用只有合并后才暴露；
3. 合并提交信息写明：合并了哪些分支、涉及哪些编号段；
4. 发现编号撞车 → **不改已有编号**（编号已被引用），把后来者整段重编号并全局替换，然后重跑验收。

### 13.4 更稳的替代方案

并行分支只产出**代码与草稿**，编号与文档统一由主线会话在合并时分配。
慢一些，但零冲突——**长期项目建议用这个**。
