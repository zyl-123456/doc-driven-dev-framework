# 文档驱动开发架构 · 用户级运行纪律（所有开发项目通用）

## 定位（老大常设命令，2026-09-04）

**只要涉及软件开发项目，一律以本架构推进。** 三层分工：**事实层**（项目内五文档，唯一事实源）+ **行为层**（本技能，纪律自动加载）+ **触发层**（**已升级为平台钩子**，见下）。

**触发层现状（2026-09-12 挂载 · 钩子 v2）**：`~/.workbuddy/settings.json` 的 `hooks` 字段已挂 `doc-driven-guard.py`（`~/.workbuddy/hooks/`；权威源 = 母版 `hooks/`）——
- **不内嵌任何纪律文字**：`SessionStart` 与 `UserPromptSubmit` 都**实时读项目里的 `00` 文档**，按章节关键词提取「落档纪律 / 收尾四步 / 证据裁决」再注入；母版一改立即生效，无副本漂移；
- `SessionStart` 注入上述纪律要点 + 项目当前快照；`UserPromptSubmit` 每轮注入**会变的「当前快照」三行**（正在做 / 卡在哪 / 下一步），而非固定复读（治"提醒疲劳"）；快照未填时明确提示去补；
- 判定方式：从 `cwd` 向上找 `开发驱动文档/00-驱动开发规则.md`（或项目根同名文件），命中才注入，非框架项目静默放行；任何异常都输出 `{"continue": true}`，绝不阻断；
- 早先"不建定时任务、由即时对齐审计替代"的裁决已被此钩子取代（钩子是推、审计是查，两者并存）。

新项目未建框架 → 先执行姐妹技能 `doc-driven-framework-porting`（本地模板 **v4** 直接生成，三分钟建好）；已有框架 → 按下方纪律运行。**换新设备** → 见 `deploy-kit/README-新设备部署.md` 或人看的 `QUICKSTART-新设备手把手教学.md`（两步：`install.py` 装能力层 + `init-master-workspace.py --init-git` 建**母版工作区 / 顶层设计目录**）。**模板母版** = 母版工作区（老设备为 `D:\000-me-work\top_design`；新设备为自选的顶层设计目录，如 `D:\top_design`）——**它是唯一权威源**，技能 `templates/` 只是发布副本；改了母版必须跑 `sync-master.py`（它会把母版**自动推到技能 templates**，这样建新项目才带最新规则）。

## 进入项目的固定动作

1. **入口**：先读项目根 `START_HERE.md`（四层阅读路径），按"我想…"表定位文档；**禁止上来全量读五文档**。
2. **先看「当前快照」**（正在做 / 卡在哪 / 下一步）——全文件唯一每轮更新的信息，一眼知道项目现在在哪。
3. **识别任务类型** → 走对应闭环。

### 接手既有项目（换会话 / 换人 / 隔期回来）

**触发**：不是从零开始的项目，而是已经有人/有会话推进过。**不要急着改代码。**

1. 读 `START_HERE`「当前快照」→ 现在在哪、卡在哪、下一步该做什么；
2. 读「第二层 全貌」→ 项目是什么；
3. 读 `04` 最近 3 条里程碑 + **坑位速查表** → 刚发生了什么、踩过什么坑（**先查表再动手**，省掉重复踩坑）；
4. 读 `03`「环境与运行」→ **亲手把它跑起来**；跑不起来先解决环境，别急着写代码；
5. **向老大复述一遍自己的理解并请其确认**——理解偏了要此刻发现，不要等做完才发现；
6. 确认无误后按闭环六步推进；本轮结束照常走收尾四步。

## 闭环六步（需求 → 验收可回流循环）

1. 人类在 `01` 说目标/需求/约束/验收标准（AI 协助整理落档，实质内容须人类确认）。**REQ 一律 EARS 句式**（老大 2026-09-04 批准）："**当〈触发条件〉时，系统应〈可验证的响应〉**"，禁止模糊表述；人类的"怎么判断效果好"转写为可验证验收条款（A-xxx）。
2. AI 转化技术事项落 `02`（TECH-xxx）；歧义登记 Q-xxx 问人类，或 ASM-xxx 保守假设后推进。
3. AI 设计落 `03`（D-xxx：口径、公式、交互规则、验收样例）。
4. AI 实现，里程碑/偏差/坑**当场**落 `04`（M-xxx + 坑位速查表）。
5. 人类按 `01` 验收标准跑 `verify.py`；需求变化先改 `01` 再同步下游。
6. 使用反馈进 `01` 反馈区，确认后转新 REQ 或修订。

## 文档权限矩阵（硬规则）

| 文档 | 人类（老大） | AI |
|---|---|---|
| `00-驱动开发规则` | 读、批准边界类条款变更 | 写；安全边界/交付铁律/权限分配等**边界条款改动须老大批准** |
| `01-人类需求描述` | **主权**（读、写、裁决） | **受托维护**（格式整理、登记原话；实质内容须确认/授权，越权即违例回滚+04 记偏差） |
| `02/03/04` | 读（可直接改，AI 不覆盖，按证据裁决对齐） | **全权**（AI 专属） |
| `START_HERE` | 读 | 全权 + 结构性变更**必须**同轮同步 |

## 收尾四步 + 即时对齐审计（每轮沟通/推进完成后立即执行）

**收尾四步**（缺一 = 任务未完成）：
a. 关键结论已落档（01 / 04）——没有落档的结论对后续会话不存在；
b. `verify.py` 全绿（退出码 0；Windows 工作站 `E:\anaconda\python.exe verify.py`）；
c. git 提交完成、工作区干净（`git status --porcelain` 为空）；
d. 同轮同步 `START_HERE.md`：① 目录/模块/核心文件增删或状态翻转；② **「当前快照」三行更新为最新状态**——它是下一个接手者的第一站，也是 `verify.py` 项目态会判 FAIL 的项。

**即时审计**：
- 对照权限矩阵复核本轮改动是否越权；
- 本轮有 REQ/TECH/D 变动 → 抽查编号跨文档链路（01 的 Q ⊆ 02 登记、02 的 ASM ⊆ 04 登记簿、03 的 D 可溯源）；
- 问题**当轮修复**，修不了的登记 04 偏差并明示老大。

## 歧义处理分级

- 保守假设可推进 → ASM-xxx 登记后直接做，事后验证；
- 根本性改变含义 → Q-xxx 登记后**停手等老大裁决**。

## 红线（按项目 00 文档领域扩展为准，通用底线）

- 用户数据默认仅本地；云端上传、无关危险权限、遥测默认关、第三方 SDK 引入——均须人类单独授权/登记。
- 交付铁律（老大 2026-08-27 命令）：**先 Windows 端可测试预览 → 老大确认 → 再打正式 APK**。
- 敏感数据不进版本库、不写死源码。

## 编号体系

`REQ`（01 需求）/ `TECH`（02 事项）/ `D`（03 设计）/ `M`（04 里程碑）/ `ASM`（04 假设）/ `Q`（待裁决）/ `C`（约束）/ `A`（验收标准）/ `SEC`（安全条款）。新内容并入既有文档，**不按需求新建说明文件**；`01–03` 只留当前有效内容，`04` 留关键事实与证据。

**单功能 spec ≤800 行红线**（Anthropic 实测阈值，老大 2026-09-04 批准）：任一功能的 REQ+TECH+D 合计超 800 行必须拆分为多个功能——文档过肥导致 AI 产出质量骤降。

**触发式归档（v4 硬阈值，到点必须压，不是"应该"）**：里程碑 >20 条 / `04` 验收表 >30 行 / `REQ` >40 条 / `04` 全文 >400 行 / `START_HERE` 里程碑索引 >20 条——触发即压缩（已完成满 3 个月的压成一行索引，细节交版本历史）。`verify.py` 对 `04` 行数、里程碑条数、验收表行数自动对账，超限即 FAIL。

## 并行开发（多会话 / 多分支）

同时开多个会话或多条分支推进时，按 `00` 第十三节执行：

- **冻结**：`00` 与 `START_HERE` 并行期间不改（入口由主线会话在合并后统一更新）；
- **文件主权**：`01` 归老大；`02/03/04` 各分支**只用预分配的编号段**（号段登记在 `START_HERE` 当前快照里），不删不重排他人条目；
- **合并纪律**：各分支合并前自跑 `verify.py`；合并后由主线会话统一再跑一次（跨分支引用只有合并后才暴露）；发现编号撞车 → 不改已有编号，把后来者整段重编号再全局替换；
- **长期项目推荐**：并行分支只出代码与草稿，编号与文档统一由主线会话在合并时分配（慢，但零冲突）。
