# 交接与迭代优化清单

> **这份文档解决什么**：站在"要长期用、要不断交给人（或新会话）接手、要持续迭代"的项目视角，对当前框架做一遍体检。
> **每条的格式**：现象 → 证据（具体文件与行号）→ 为什么疼 → 怎么改。
> **状态**：待裁决（2026-09-12）。清单里没有"必须改"，只有"改了会更顺"。
> 与《框架评价与边界》的分工：那篇回答"这框架值不值得用、边界在哪"；本篇回答"下一步该补什么"。

---

## 零 · 结论先说

当前框架在**单次开发**场景下已经相当完整——需求、拆解、方案、记录、验收、权限，环环都在。

缺口集中在两处：

| 场景 | 缺什么 | 一句话 |
|---|---|---|
| **交接** | 缺「当前态」 | 文档记得住"做过什么"，接手的人却要翻很久才知道"现在在哪、下一步做什么" |
| **迭代** | 缺「悬置项的位置」 | 临时方案、待还的债、以后要重审的决定，没有地方放 |

这两处其实是**同一个病根**：

> **框架把「已经发生的事实」管得很好**（里程碑、坑、验收结论、偏差），
> **但「还没解决的悬置项」几乎没有位置。**

---

## 一 · 交接视角

### H1 · START_HERE 有「历史」，没有「现在」 【P0】

**现象**：`START_HERE.md` 是交接入口，四层结构为「纪律 → 全貌 → 按任务 → 历史」。
第四层"历史"只留里程碑索引，一行一条。**但没有任何一层回答交接者最先要的三个问题：现在做到哪了、有什么卡着、下一步干什么。**

**证据**：`START_HERE.md:34-37` 第四层只有 `M-000` 与"后续里程碑一行一条"；
第三层的 `{{状态}}` 列（`:27-32`）标的是"各份文档的状态"（稳定 / 进行中），**不是"项目当前阶段"**。

**为什么疼**：现在要跳进 `04` 的里程碑时间线，从最后一条往前读，自己把状态拼出来。
项目做半年、里程碑 30 条，拼一次要几分钟——而**每次交接都要重复付这个成本**。

**怎么改**：在第二层之后插一个「当前快照」小节，只写三行：

```markdown
## 当前快照（每次推进后更新，交接的第一站）
- 正在做：
- 卡在哪 / 等谁：
- 下一步：
```

配套两件事：把"更新当前快照"写进 `START_HERE` 的维护规则；`verify.py` 加一条检查（该节存在且三行非空）。

---

### H2 · 接手没有固定动作 【P1】

**现象**：行为层技能 `doc-driven-dev` 有「进入项目的固定动作」（`:20-23`），但只有两条：读 `START_HERE` → 识别任务类型。
**没有"接手一个别人做过的项目"这个场景的动作。**

**为什么疼**："不断交接"里，接手方第一轮该做什么，现在全靠自觉。理想是一张固定清单：
读快照 → 读最近 3 条里程碑 → 查坑位速查表 → **验证自己能把它跑起来** → **复述一遍自己的理解请对方确认**。

最后那步"复述确认"是交接质量的关键——**理解偏了要当场发现，不能等做完才发现**。

**怎么改**：技能里加一节「接手既有项目」，把上面五步固定下来。

---

### H3 · 「跑不起来」没有落点 【P0】

**现象**：五文档里 `03` 有测试方案（`:47-58`），但**没有环境搭建与启动步骤**——装什么、什么版本、怎么起、怎么判断起成功了、外部依赖（账号 / 服务 / 数据）去哪拿。

**为什么疼**：交接时第一个卡点永远是"跑不起来"。这一小时内文档帮不上忙，只能问原开发者——而原开发者可能已经不在了。
**这是交接里成本最高、最集中、也最容易提前消灭的一段。**

**怎么改**：`03` 新增一节「环境与运行（接手第一站）」，内容四项：
1. 依赖清单 + 版本；
2. 启动命令；
3. **"起成功了"的判断标准**（跑通什么算通了）；
4. 外部依赖与凭据**在哪拿**（凭据本身不入库，只写位置）。

---

### H4 · 关键决定记了「为什么」，没记「什么情况下该推翻」 【P2】

**现象**：`03` 第四节「关键决定」是（决定 / 理由 / 日期）三列（`:60-64`），第五节还有「已失效方案存档」（`:66-70`）——已经很接近轻量 ADR 了。
**缺的是「重审条件」**：当初选 A 不选 B，是因为"当时还没有 X"；后来有了 X，却没人知道该重新考虑。

**为什么疼**：长期项目的技术前提会被时间改变（依赖停止维护、数据量级变化、需求重心转移）。
没有重审条件 → 后人要么不敢动（把过时决定当教条），要么莽撞推翻（不知道自己踩在什么前提上）。

**怎么改**：第四节的表加一列「重审条件」，例如"若该库停止维护 / 数据量超 10 万 / 需支持多端"。

## 二 · 迭代视角

### I1 · 技术债没有落点 【P0】

**现象**：`04` 已经有三个"问题容器"——坑位速查表（**已解决**的坑，`:8-14`）、偏差与限制（**与原方案不一致**的地方，`:46-50`）、假设登记簿（**未验证**的假设，`:36-44`）。
**唯独没有"已知但暂不处理"的位置**：临时绕过、性能妥协、丑但能用的实现、"二期再说"的设计。

**为什么疼**：现在这类东西只能塞进代码注释或聊天记录 → 交接时全丢。
而长期迭代的项目，**债是必然产物，不是意外**。丢债的后果在下一次迭代才爆发：后人按理想架构改，一头撞上当年埋的临时方案。

**怎么改**：`04` 加第六节「技术债 / 待办登记」，五行表：
`TD-xxx` · 内容 · 为什么先欠着 · **什么条件下必须还** · 登记日。
关键是第四列——**没有触发条件的待办等于永远不办**。

---

### I2 · 里程碑与验收结论会无上限增长 【P1】

**现象**：`04` 第五节「已完成的验收结论」每次验收加一行（`:56-58`）；第二节里程碑每个一小节（`:16-34`）。两者**都没有归档触发条件**。
`00` 第九节（`:112-122`）有「REQ 退役」「归档节奏」，但归档节奏只说"`04` 只保留里程碑、关键证据和限制"——**没说什么条件下必须压**。

**为什么疼**：这正是《框架评价与边界》点出的「`04` 是唯一失控环节」的**根因**——和 800 行红线同一个病：**只有"应该"，没有"何时必须"**。
实测数据：真实项目 `04` 已到 449 行，占全部文档 42%。

**怎么改**：写死三条触发条件（数字可调）：
- 里程碑 > 20 条 → 已完成超 3 个月的压成一行索引（编号 + 一句话 + 哈希）
- 验收结论表 > 30 行 → 只留最近 10 行 + 按月归档索引
- 把 `04` 行数上限（如 400 行）写进 `verify.py`，超限即 FAIL

---

### I3 · REQ 退役没有触发条件 【P2】

**现象**：`00` 第九节（`:115`）要求"完成且被后续需求取代的条目压缩为索引行"，同样只有"应该"。
**怎么改**：并进 I2 的同一套触发条件（`REQ` > 40 条，或被取代超 3 个月）。

---

### I4 · 改了 A，会不会弄坏 B 【P1】

**现象**：`01` 的验收标准 `A-xxx` 是"人类可独立判断"（`:60-65`）；`03` 的测试方案是"每项测试对应某个 `REQ`/`TECH`"（`:47-58`）。
两者都是**增量视角**——"新功能怎么验"，**没有"回归清单"**：每次改动必跑哪几项保底，确保老功能没坏。

**为什么疼**：长期迭代最常见的质量事故就是"改 A 坏 B"。
而 `verify.py` **只对账文档结构，不测功能**——它全绿不代表功能没坏（《框架评价与边界》§7-4 已点明这一点）。

**怎么改**：`03` 测试方案加一节「回归清单（改动必跑）」：列 5–10 条最关键的功能路径，标出哪些能脚本化、哪些要人工。**不用多，但要固定。**

## 三 · 机制视角

### M1 · `verify.py` 可以查「交接就绪」 【P1】

**现象**：`verify.py` 现在查的是"文档结构完整 + 编号链条一致 + 安全条款齐全"——这些是**框架自洽性**。
**没查"交接就绪度"**：当前快照填了没、环境节在不在、里程碑数是否失控。

**为什么疼**：框架里有大量"靠自觉"的条款（800 红线、`04` 归档、REQ 退役）。
**凡是没被脚本检查的规则，长期看都会退化**——这不是不信任谁，是注意力天然有限。

**怎么改**：加 3 条最容易被忘的检查，把"提醒"变成 FAIL：
1. `START_HERE` 当前快照三行非空（防"忘了更新"）
2. `04` 行数 / 里程碑条数在阈值内（防膨胀）
3. 坑位速查表有实际内容（防"有坑没记"）

---

### M2 · 多会话并行时，五文档没有分工规则 【P0】

**现象**：权限矩阵假设的是"**一个人类 + 一个 AI**"（`00` 第三节 `:56-63`）。
但实际可能**同时开多个会话 / 多分支并行开发**——这正是 `parallel-branch-dev` 技能要做的事。

此时 `02` / `03` / `04` 都是"AI 全权"，**两个 AI 各改一份，合并必冲突**；
更隐蔽的是：两个会话各自记 `M-xxx`、各自动编号，**编号会撞车**。

**为什么疼**：并行是长期项目的常态（一条主线 + 若干实验），而框架在这个场景下**不是规则不好，是空白**。
冲突和编号撞车会在合并那一刻集中爆发——那是最不该出问题的时候。

**怎么改**：`00` 新增一节「并行开发约定」（或在第十二节领域扩展里按项目定）：
- **文件主权**：`01` 归人类（合并点唯一）；`02/03/04` 各并行分支**只写自己预分配的编号段**
- **编号分段预分配**：分支 A 用 `M-100~199`、分支 B 用 `M-200~299`，避免撞车
- **合并纪律**：各分支自跑 `verify.py`；合并后由主线会话统一再跑一次
- **更稳的替代**：并行分支只产出代码与草稿，编号统一由主线会话分配（慢但零冲突）

---

### M3 · 换设备的路径没进行为层技能 【P2】

**现象**：钩子挂载写在 `doc-driven-dev`（`:13-16`），但"换新设备怎么把这套能力搬过去"只在板块技能 `doc-driven-framework-porting` 里。
路径是：`doc-driven-dev` ← 行为层（每次开发都加载）；`doc-driven-framework-porting` ← 只在"建新项目"时才被想到。
**换设备时，行为层找不到路。**

**怎么改**：`doc-driven-dev` 加一行指向（"换设备 → 见 `deploy-kit/README-新设备部署.md`"）。

## 五 · 优先级汇总

| 优先级 | 条目 | 一句话 |
|---|---|---|
| **P0** | H1 | `START_HERE` 加「当前快照」（交接第一站） |
| **P0** | H3 | 加「环境与运行」落点（解决"跑不起来"） |
| **P0** | I1 | `04` 加「技术债登记」（给悬置问题一个位置） |
| **P0** | M2 | 补多会话并行的文件主权与编号分段规则 |
| **P1** | H2 | 技能加「接手既有项目」固定动作 |
| **P1** | I2 / I3 | `04` 与 `REQ` 的归档触发条件 + `verify.py` 阈值 |
| **P1** | I4 | `03` 加「回归清单（改动必跑）」 |
| **P1** | M1 | `verify.py` 加「交接就绪」检查 |
| **P2** | H4 | 关键决定加「重审条件」 |
| **P2** | M3 | 技能补换设备指引 |
| — | F1 | 修 v2 笔误（可直接改） |

**P0 四条的共同点**：都是**"给悬置项一个位置"**——
现在在哪（H1）、怎么跑起来（H3）、欠了什么债（I1）、并行时谁说了算（M2）。

框架已经把"已发生的事实"管得很好了。下一步是**把"还没解决的"也管起来**。

---

## 六 · 一句话总纲

> **单次开发，这套框架够用；
> 长期迭代 + 高频交接，它缺的不是"规则不够严"，而是"悬置项没地方放"。**

补上这四个位置，框架就从"能记录历史"变成"能支撑接力"。
