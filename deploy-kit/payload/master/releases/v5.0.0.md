# v5.0.0 · 减少重复，按任务协作

日期：2026-10-10。前一版本：v4.0.0（提交 16e6c71）。本版保留为预发布记录，正式使用 v5.0.1。

## 为什么改变

人类已确认上一轮审阅建议并授权落实：保留需求、关键理由、当前状态和证据，减少重复文档、每轮强制流程与无依据硬阈值，并建立可追溯的 GitHub 版本管理。

## 与 v4 的区别

| 方面 | v4 | v5 |
|---|---|---|
| 任务粒度 | 每轮沟通均走收尾 | 实质任务、决定或交接时维护 |
| 简单改动 | REQ / TECH / D / M 链 | 可直接修改、检查与必要的一行记录 |
| 信息位置 | 问题和假设多表同步 | 每条信息唯一落点，其余引用 |
| 人类确认 | 接手先复述等确认 | 已有授权持续有效，实质歧义才确认 |
| 证据 | 固定配置优先序 | 按意图、实现、理由、进展分别判断 |
| 规模 | 超限 FAIL，三个月归档限制 | 可配置提醒，按检索成本整理 |
| 验收 | 关键词与框架格式检查 | 显式定义、引用、相对链接和范围声明 |
| 工作区 | 日常未提交即失败 | 日常报告输入；正式发布要求已提交 |
| 提醒 | 每条消息重复收尾纪律 | 可选短入口；无变化消息不重复注入 |
| 来源 | 本机技能可反向覆盖部署副本 | 仓库内源生成副本 |
| 版本 | 里程碑提交，无正式变更记录 | 版本、标签、差异说明、CI 与发布产物 |

## 迁移

新项目复制模板即可；verify.py 自动识别母版与项目，支持明确指定 --mode。
已有项目保留所有人类需求、设计和证据，只按授权迁移规则、入口与检查器。旧 Q / ASM 表可合并为唯一落点，不清除仍有价值的决定。
WorkBuddy 用户更新技能和钩子后，核对旧全局治理记忆是否仍含“一律使用”“最高优先级”等旧规则；安装器不会自动改写人类记忆。真实客户端触发需要另行验证。
Codex 可使用自己的项目指令指向入口；不复制 WorkBuddy 配置。

## 验证

- 本地 Python 3.12.10：`python -m unittest discover -s tests -v`，25 项行为回归通过；包括错误配置不覆盖、重复安装不增备份、旧钩子升级、中文及带空格路径、包清单和 ZIP / tar.gz 内容与哈希。
- `python verify.py`：母版文档结构检查通过；日常输出明确区分已提交输入与工作区变更。
- `python deploy-kit/sync-master.py --check`：仓库内发布副本与清单一致；差异或未知副本的失败行为有回归覆盖。
- 两个技能均通过 skill-creator 的 quick_validate.py 结构验证；该验证不证明模型实际遵守。
- 六份核心 Markdown：v4 39,925 字节 → v5 8,995 字节，减少约 77.5%。这不是 tokenizer 测量，也不是开发效果改善比例。
- GitHub Actions 配置 Ubuntu / Windows、Python 3.9 / 3.12 矩阵；实际远端状态查看对应提交的 Actions，不把本地通过等同于远端通过。
- 发布输入在提交后执行 `python verify.py --release`；通过后打包并将产物附到该版本 Release。产物各自的 SHA-256 见附带清单。

## 已知限制

GitHub CI 的 Ubuntu 检查通过，但 Windows 3.12 检查发现同步模块的中文输出在 CP1252 下报错（运行 37963039209）。修复和额外回归由 v5.0.1 记录；不移动本版已有标签。

未开展模型效果对照，不能承诺 token 节省比例或成功率提升。相对链接只检查文件存在，不检查章节锚点或网页可用性。钩子脚本测试不代表客户端已经触发；本地测试不代表 GitHub CI 已运行。
