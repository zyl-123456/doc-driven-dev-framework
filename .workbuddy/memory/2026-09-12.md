## 追加：对框架的技术评价与适用边界（老大要求评估）

**产出**：`框架评价与边界.md`（12.5KB），已登记进 README 目录结构。配 3 张可视化（人类/AI 记忆差异、加钩子前后触发链路、收益成本随交接次数曲线）。

**核心论点**
1. 框架的本质：**给无状态协作者（AI）配的体外记忆与作业纪律**。人类同事靠自身记忆衔接会话；AI 每次从零醒来，文档不是可选规范而是必要设施。→ 这解释了"有人觉得没意义 / 老大觉得有意义"的分歧：双方说的场景不同，都对。
2. 判据不是项目大小，而是 **"要被交接多少次"**（换会话/换人/隔期回来）。约 3 次交接为盈亏平衡点：成本一次性、收益按次累积。
3. **加钩子的机制意义**：前两层（事实层死文件、行为层需主动调）本来就有，钩子决定它们是否真被用到。加钩子前有三个漏点——判断漏（没认成开发任务）、加载漏（没读 START_HERE）、收尾漏（忘落档/验收/提交）；钩子消除判断漏，大幅降低另两个。**且让失效从"静默"变"显性"**（看本轮有无注入提醒即可判断）。
4. **诚实的界线**：钩子保证"看到"不保证"做到"。它是防漏保险，不是合规强制执行。
5. **钩子的代价**：上下文成本（每轮数十 token）、提醒疲劳、**新增耦合点**（钩子内嵌的纪律文字是 00 文档条款的副本，改母版不会自动同步——又一个"文档与现实打架"风险源）、运行依赖解释器绝对路径。
6. **不限制 AI 能力**：只约束「不能擅自改人类需求 / 不能不留证据 / 不能没验收就宣布完成」三条过程纪律，技术实现（选型/架构/库/数据结构）全权放开。真正会伤能力的是**文档膨胀**（800 行红线依据），而该红线目前**无强制机制**。
7. **框架不会让错误决定变对**——只解决信息丢失，不解决判断失误。

**实测数据（写进评估文档）**
- 母版自身体量：646 行 / 39.6KB（可忽略的一次性成本）。
- 真实项目「事务伴侣」：**1,129 行 / 103KB**，对照源码 32 个文件。
- **`04-实现过程记录.md` 449 行 / 43.9KB，占全部文档 42%** —— 膨胀最快的一环；`01–03` 因"只留当前有效内容"的规则被结构性地压住了，说明自我约束条款有效，但**对 `04` 约束偏弱**。

**给出的改进建议（老大未裁决）**
1. 给 `04` 设硬上限或定期归档机制（里程碑超 N 条时压成索引行，细节交 git）——现在只有"应该压缩"，缺"何时必须压缩"。
2. 800 行红线纳入 `verify.py`，超限即 FAIL。
3. 钩子改为**实时读** `00` 文档关键条款，而非内嵌副本，消除同步耦合。
4. 钩子"提醒疲劳"暂无度，是否按任务类型分级注入待观察（分级又会回到"靠判断"，需权衡）。
