## 已知坑

- **编号抽取正则必须加负向断言**（2026-09-12 首测命中）：`REQ-001` 内含 `Q-001`、`ASM-000` 内含 `M-000`，朴素 `re.findall("Q-\\d{3}")` 会误报「悬空引用」。写法：`(?<![A-Za-z])Q-\d{3}`。
- **占位符成对一致性**：`02` 的 ASM 行与 `04` 假设登记簿的 ASM 行必须同增同删，否则 `verify.py` 的跨文档一致性检查会 FAIL。
- **验证要跑两种布局**：母版目录（文档在根）与真实项目布局（文档在 `开发驱动文档/`）都要能 28/28 通过。

## 新设备迁移（2026-09-12 建）

新设备上要让 WorkBuddy 具备同样能力，必须搬**四样**（少一样都会"看起来装了、其实没用"）：① 技能 `doc-driven-dev`；② 技能 `doc-driven-framework-porting`（含 templates）；③ 钩子脚本；④ `settings.json` 的 `hooks` 字段 + `MEMORY.md` 治理段。

**关键坑**：钩子命令写的是解释器**绝对路径**（老设备 `E:/anaconda/python.exe`）——直接拷 `settings.json` 到新设备会因路径不存在而静默失效，**必须在目标机重新生成**。

**一键通道**：`deploy-kit/install.py`（跨平台、幂等、改动前自动备份 `.bak-<日期>`、装完自检）。实测：首次 15/15 PASS、母版 `verify.py` 28/28 PASS；重复跑仍 15/15（钩子与记忆段提示"已跳过"）。
参数：`--dry-run` / `--home`（测试用）/ `--master-dir` / `--with-codebuddy`（钩子配置路径兜底）。

**待实测**：WorkBuddy 桌面版是否真读 `~/.workbuddy/settings.json` 的 `hooks`（官方 IDE 文档写 `.codebuddy/settings.json`，第三方文章实测 `~/.workbuddy/` 有效）。未生效时用 `--with-codebuddy` 补写。

## 框架评价（2026-09-12）

完整评估见本目录 `框架评价与边界.md`。要点：

- **本质**：给无状态协作者（AI）配的体外记忆 + 作业纪律。不是"文档管理规范"。
- **适用判据**：看**交接次数**（换会话/换人/隔期回来），约 3 次为盈亏平衡点；成本一次性、收益按次累积。
- **钩子的机制意义**：前两层（事实层/行为层）本就有，钩子决定它们是否真被用到；消除"判断漏"，并让失效从静默变显性。但**只保证"看到"，不保证"做到"**。
- **钩子的新增负债**：内嵌的纪律文字是 `00` 条款的副本 → 改母版不会自动同步，是新的"文档与现实打架"风险源。
- **真正的风险是文档膨胀**（约 800 行/单功能为红线），**该红线目前无强制机制**。实测事务伴侣 `04` 占文档总量 42%。
- **待裁决改进**：① `04` 设硬上限/归档机制；② 800 行红线纳入 verify.py；③ 钩子改为实时读 00 文档而非内嵌副本。

## 文档导读（2026-09-12）

逐份文档的行数、章节骨架、维护权责、填写时机，见本目录 `文档导读.md`。核心数据：

- **进项目的只有 7 份 = 649 行 / 9,170 个中文字，实质内容 437 行**（≈两篇长文）。
- 厚薄是刻意的：`00` 最厚（204 行，承载全部规则）、`02` 最薄（46 行，没需求就是空的）、`04` 会最厚（流水账）。
- **模板态 vs 项目态**（事务伴侣）：649 行 → 1,129 行；其中 `04` 58 → **449 行（↑7.7 倍）**，其余最多翻 2 倍多。规则文档 `00` 基本不增长（204→187），说明框架没跑偏。
- 结论：**模板态偏薄是设计选择**（骨架对、留白够），填满反而不好用；真实价值在填进去的内容。
