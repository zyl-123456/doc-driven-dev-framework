# 文档驱动开发框架 · 通用模板 v3

> **这是什么**：一套**开工前就能套用**的开发文档模板。你在动手做任何一个软件 / 项目之前，先把这套文件复制过去，用最少的字把"要做什么"写下来；之后我们一起边聊边开发，这套文档跟着一起长，最后变成这个项目的完整台账。
>
> **母版位置**：`D:\000-me-work\top_design`（本目录即权威母版，改动以这里为准）
> **模板版本**：v3　|　**定稿日期**：2026-09-12

## 一、用大白话讲：这套东西到底干嘛的

做项目最怕的不是难，是**忘**和**对不上**：

- 上周聊定的事情，这周开个新会话，没人记得了 → **丢了**
- 文档上写着 A 方案，代码其实早改成 B 了，谁也不知道该信谁 → **对不上**
- 功能"感觉做完了"，结果验收没跑、文档没写、代码没提交 → **收尾漏了**
- 我说"想要顺手一点"，做出来的东西我觉得不顺手 → **没说到一块去**

这套模板就是针对这四件事的。它相当于给项目配一本**双方共用的台账**：

| 台账册子 | 里面写什么 | 谁来写 |
|---|---|---|
| `00-驱动开发规则.md` | 规矩本：怎么协作、什么算做完、底线是什么 | 规则，基本不动 |
| `01-人类需求描述.md` | **你要什么**：目标、需求、验收标准、使用反馈 | **你（老大）说了算** |
| `02-需求技术拆解.md` | 我把它翻译成哪些技术问题要解决 | AI |
| `03-技术实现方案.md` | 我打算怎么做、关键规则定成什么样 | AI |
| `04-实现过程记录.md` | 实际做完了什么、踩了哪些坑、结论是什么 | AI |
| `START_HERE.md` | 门牌：新会话从这进，按需翻册子，不用全读 | AI |
| `verify.py` | **对账单**：一条命令，自己核一遍有没有漏 | 机器 |

还有一本"行为手册"不放在项目里，是**跨项目共用**的（用户级技能 `doc-driven-dev`）——它保证我每次进项目都按同一套纪律干活。

**核心好处**：隔半个月开新会话、或者换个人接手，翻台账就接得上，不用你从头再讲一遍故事。

## 三、新项目怎么用（5 分钟开工清单）

### 第 0 步：建目录

在新项目根目录下建一个 `开发驱动文档/` 文件夹，然后按下面的结构摆：

```
<你的新项目>/
├── START_HERE.md              ← 从模板复制到项目根
├── verify.py                  ← 从模板复制到项目根
├── 开发驱动文档/
│   ├── 00-驱动开发规则.md      ← 五份文档放这个文件夹里
│   ├── 01-人类需求描述.md
│   ├── 02-需求技术拆解.md
│   ├── 03-技术实现方案.md
│   └── 04-实现过程记录.md
└── （你的代码目录…）
```

> **图省事的办法**：直接跟我说一句"给 XX 项目建文档驱动架构"，我会调用技能 `doc-driven-framework-porting` 自动生成整套，比手工复制快得多。

### 第 1 步：替换占位符

- **机械替换**（全库一次换完）：`{{PROJECT}}` → 项目名，`{{DATE}}` → 当天日期 `YYYY-MM-DD`。
- **描述性占位**（要逐条按实际填）：`{{一句话}}`、`{{假设}}`、`{{状态}}` 这类，一条条填掉或删掉。
- **特别注意**：`02` 里的 `ASM` 行和 `04` 假设登记簿里的 `ASM` 行**必须同增同删**——留一个悬空的引用，`verify.py` 会直接报 FAIL。

### 第 2 步：只填这几处，就可以开工了

先不用把模板填满，**填最少的三处**就能开始：

1. `01` 的**协作模式授权**（写明"需求你定、技术我定"，日期签上）；
2. `01` 的**项目目标**（一段话说清做什么、给谁、核心价值）；
3. `00` 的**第十二节领域扩展**（先填 12.5 领域红线，其余空缺着）。

然后就可以开口讲需求了——**用大白话说"我想要什么效果、我怎么判断好不好"就够了**，我会把它转写成 `REQ` 标准句式（EARS 格式：当〈什么情况〉时，系统应〈做什么〉），登记进 `01`。

### 第 3 步：初始化版本库

```bash
git init -b main
git add -A
git commit -m "M-000 项目初始化：建立文档驱动框架"
```

首次提交后跑一次验收：

```bash
python verify.py          # 或 E:\anaconda\python.exe verify.py
```

看到**全绿、退出码 0**，框架就算立起来了。

## 四、之后日常怎么跑（一个循环）

1. **你说需求** → 我整理进 `01`（实质内容你点头我才写）。
2. **我拆技术问题** → 进 `02`；有歧义要么记 `Q-xxx` 停下来问你，要么记 `ASM-xxx` 假设后先干。
3. **我定实现方案** → 进 `03`（把模糊话变成死规则 + 可手工对账的验收样例）。
4. **我写代码** → 过程、偏差、踩的坑随手进 `04`。
5. **你验收** → 跑 `python verify.py`；需求要变，先改 `01` 再往下同步。
6. **你用出问题 / 有新想法** → 记进 `01` 的反馈区，确认后变成新 `REQ`，回到第 2 步。

**每一轮结束我都要做完四件事**（缺一件就算没干完）：结论落档 → 验收全绿 → 版本提交干净 → 根入口同步。

## 五、几条容易踩的坑（模板自带提醒）

- **别按需求新建文件**。新需求就并进 `01`，靠编号串联，不要一篇需求一个 md——文件一散，台账就废了。
- **单功能别写太肥**。一个功能相关的 `REQ` + `TECH` + 设计合计超过 800 行，就该拆成两个功能了；文档太胖会让 AI 的产出质量明显下滑。
- **模板里的话不是文档**。`<!-- -->` 里的和 `>` 引用块里的都是**给我看的说明**，正式填写时该删就删，别把说明当需求抄进去。
- **文档和现实打架时，改文档**。真实状态的可信度排序是：运行配置 > 目录结构 > 版本历史 > 文档。文档永远排最后，因为它最容易滞后。

## 六、和"技能"的关系（防止两套模板打架）

这套框架有**两个载体**，职责说清楚，避免后面对不上：

| 载体 | 位置 | 角色 |
|---|---|---|
| **本目录（母版）** | `D:\000-me-work\top_design` | **唯一权威源**。改规则、加条款，都改这里 |
| **技能副本** | `~/.workbuddy/skills/doc-driven-framework-porting/templates/` | 冷启动时给新项目复制用的**发布副本** |
| **行为层技能** | `~/.workbuddy/skills/doc-driven-dev/` | 不进项目，跨项目共用：每次开发自动加载纪律 |

> **规矩**：母版改了、并经你验收确认后，再同步到技能副本；**不要两边各改各的**。同步动作跟我说一句就行。
